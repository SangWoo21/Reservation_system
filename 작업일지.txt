[문제 1: S3 다운로드 404 오류]

증상:
- EC2 인스턴스가 시작되고 Java 설치는 성공하지만
  S3 jar 다운로드 단계에서 아래 오류 발생:
  "fatal error: An error occurred (404) when calling the HeadObject operation:
   Key "reservation-0.0.1-SNAPSHOT.jar" does not exist"

원인 분석 과정:
- 처음에는 IAM 권한 문제라고 판단 → IAM Role 정책 재확인했으나 정상
- 그 다음 S3 리전 플래그 누락 의심 → --region ap-northeast-2 추가 (버전 4)했으나 동일 오류
- S3 콘솔에서 실제 파일명과 버킷명 직접 확인 요청
  → 실제 버킷명: project-reservation-jar-247448832103-ap-northeast-2-an
  → User Data에는: project-reservation-jar (잘못된 이름)
- S3 버킷 생성 시 AWS가 계정 ID + 리전을 붙여 실제 버킷명을 자동 생성했는데
  User Data에는 원래 의도한 짧은 이름만 입력되어 있었음

해결:
- Launch Template 버전 5 생성
- S3 URI를 정확한 버킷명으로 수정:
  s3://project-reservation-jar-247448832103-ap-northeast-2-an/reservation-0.0.1-SNAPSHOT.jar
- 이후 시스템 로그에서 S3 다운로드 성공 확인

[문제 2: ALB Target Group unhealthy (헬스체크 실패)]

증상:
- S3 다운로드 성공, 앱 실행은 되는 것 같은데 ALB Target Group이 계속 unhealthy
- 이로 인해 ASG가 해당 인스턴스를 비정상으로 판단하고 계속 교체하는 루프 발생

원인 분석 과정 (3단계):

단계 1 - 헬스체크 경로 문제 의심
- ALB 헬스체크 경로가 /로 설정되어 있었음
- /는 Spring Security의 anyRequest().authenticated()에 걸려 401 반환 가능
- /actuator/health로 변경 시도 → 여전히 unhealthy

단계 2 - Actuator 미포함 문제 발견
- build.gradle 확인 결과 spring-boot-starter-actuator 의존성 자체가 없었음
- /actuator/health 경로가 존재하지 않으므로 404 반환 → unhealthy
- spring-boot-starter-actuator 추가 후 재빌드/재배포 → 여전히 unhealthy

단계 3 - HTTPS 강제 설정 문제 발견
- app.log를 직접 확인하기 위해 Fleet Manager → Session Manager 접속
- 로그 확인: 앱은 정상 실행 중이었음
- 분석: ALB는 EC2에 HTTP(8080)로 헬스체크를 보내는데,
  SecurityConfig의 requiresChannel().anyRequest().requiresSecure() 설정이
  모든 HTTP 요청을 HTTPS로 302 리다이렉트하고 있었음
  → ALB가 302를 받으면 unhealthy로 판정
- 근본 원인: HTTPS 강제는 CloudFront/ALB 레벨에서 이미 처리하고 있으므로
  EC2 내부에서 중복으로 강제할 필요가 없었음
- 해결: SecurityConfig에서 requiresChannel 블록 전체 제거
- 재빌드/재배포 후 healthy 확인

[문제 3: RDS 연결 실패 (크로스 리전 접속 불가)]

증상 (app.log):
- "Communications link failure"
- "java.net.SocketTimeoutException: Connect timed out"
- Hibernate가 SessionFactory 초기화 중 DB 연결 시도에서 타임아웃

원인 분석 과정:

단계 1 - EC2 접속 방법 탐색
- SSH 접속 시도: EC2가 프라이빗 서브넷에 있어 퍼블릭 IP 없음 → 접속 불가
- SSM Session Manager 시도: SSM Agent가 "no valid credentials" 오류
  → 원인: 프라이빗 서브넷에 NAT Gateway는 있으나 SSM VPC 엔드포인트 없음
  → 해결: IAM Role에 AmazonSSMManagedInstanceCore 정책 추가 후 재시도했으나 여전히 오프라인
- Fleet Manager 시도 → 성공적으로 터미널 세션 접속 가능

단계 2 - 로그 분석
- sudo tail -100 /home/ec2-user/app.log 실행
- SocketTimeoutException 확인
- RDS 엔드포인트 확인: reservation.c9iqgkqq2vql.ap-southeast-2.rds.amazonaws.com
  → ap-southeast-2는 시드니 리전!
- EC2는 서울(ap-northeast-2), RDS는 시드니(ap-southeast-2) → 크로스 리전 연결

단계 3 - 근본 원인 파악
- RDS 생성 시 팀원이 실수로 시드니 리전에 생성
- 시드니 RDS 보안 그룹에 3306 포트 인바운드 규칙이 없었음
- 크로스 리전이라 EC2 보안 그룹 참조 불가 → 0.0.0.0/0으로 임시 개방

해결 (임시):
- 시드니 RDS 보안 그룹에 MySQL/Aurora 3306 포트 0.0.0.0/0 인바운드 규칙 추가
- [보안 주의] 이후 상우와 협의하여 RDS 서울 이전 또는 IP 제한으로 교체 필요

[문제 4: Redis(ElastiCache) 연결 실패 (TLS 미설정)]

증상 (app.log):
- "Unable to connect to master.project-reservation-redis.nm3ono.apn2.cache.amazonaws.com/<unresolved>:6379"
- "io.lettuce.core.RedisCommandTimeoutException: Connection initialization timed out after 3 second(s)"
- RDS 연결 성공 후 앱은 기동되었으나 스케줄러에서 Redis 연결 실패 반복

원인 분석 과정:

단계 1 - 보안 그룹 문제 의심
- EC2 보안 그룹 확인: 인바운드 6379 from 10.0.0.0/8 규칙 존재
- ElastiCache 보안 그룹 확인: 동일하게 6379 from 10.0.0.0/8 존재
- 보안 그룹은 정상으로 보였으나 여전히 연결 실패

단계 2 - DNS 해석 문제 의심
- <unresolved> 키워드 주목
- nslookup 실행: 정상적으로 10.0.129.216으로 해석됨 → DNS 문제 아님

단계 3 - 네트워크 연결 테스트
- nc -zv 명령어: not found
- bash TCP 테스트: timeout 5 bash -c 'cat < /dev/tcp/10.0.129.216/6379' → 연결 실패
- 같은 VPC임에도 TCP 연결 자체가 실패

단계 4 - ElastiCache 보안 그룹 재확인
- 소스를 CIDR(10.0.0.0/8) 대신 EC2 보안 그룹 ID(sg-0d4f24a1513fcc372)로 변경
- 여전히 연결 실패

단계 5 - ElastiCache 설정 확인
- ElastiCache 클러스터 상세 설정 확인
- "In-transit encryption: 활성화됨, 전송 암호화 모드: 필수(required)" 발견
- ElastiCache가 TLS 연결만 허용하는데 앱은 일반 TCP로 연결 시도하고 있었음
- bash TCP 테스트가 실패했던 이유: ElastiCache가 TLS 아닌 연결을 즉시 끊어버림

단계 6 - TLS 연결 테스트로 가설 검증
```
openssl s_client -connect master.project-reservation-redis.nm3ono.apn2.cache.amazonaws.com:6379
→ CONNECTED, Verification: OK, TLSv1.2, Cipher: ECDHE-RSA-AES128-GCM-SHA256
```
→ TLS 연결은 완벽하게 성공 → 네트워크/보안 그룹은 정상, TLS 설정 누락이 원인

해결:
- application.yml에 SSL 설정 추가:
  spring.data.redis.ssl.enabled: true
- 재빌드/재배포 후 Redis 연결 성공

문제 1: SimpleEmailServiceMailSender 빈 생성 실패
- 증상 (app.log):
  "No qualifying bean of type 'io.awspring.cloud.ses.SimpleEmailServiceMailSender' available"
- 원인: Spring Cloud AWS 3.x에서 SES 자동 구성이 해당 타입의 빈을 직접 등록하지 않음
- 해결: 주입 타입을 SimpleEmailServiceMailSender → MailSender 인터페이스로 변경
  (Spring Cloud AWS가 MailSender 타입으로 빈을 등록하므로 정상 주입됨)

문제 2: SES API 호출 시 403 Forbidden
- 증상: curl로 /api/email/send 호출 시 HTTP 403
- 원인 분석:
  - Spring Security CSRF 보호가 활성화되어 있어 POST 요청에 CSRF 토큰 필요
  - 첫 GET 요청으로 CSRF 토큰 획득 후 X-XSRF-TOKEN 헤더에 포함하여 재요청
  - 여전히 403 반환
  - 원인: Spring Security 6에서 CSRF 토큰 방식이 변경됨
    기존: 쿠키 값 = 헤더 값이면 통과
    변경: XOR 마스킹된 토큰을 사용하므로 쿠키 원본값을 헤더에 그대로 전송하면 검증 실패
- 근본적 해결: REST API는 stateless 구조이므로 CSRF 보호가 불필요
  (CSRF는 브라우저 세션 기반 공격에 대한 방어인데, 이 API는 HMAC 토큰으로 인증)
  SecurityConfig에서 .csrf(csrf -> csrf.disable())으로 변경

결과:
- curl 테스트 성공: {"message":"Verification code sent","expiresIn":"5 minutes"}
- twinf1004@hufs.ac.kr 수신함에 인증 코드 이메일 정상 수신 확인

[ASG Lifecycle Hook 코드 통합]

배경:
- 팀원(상우)이 Lifecycle Hook 처리를 위한 코드를 추가/수정:
  - LifecycleHookService.java (신규): IMDSv2로 인스턴스 ID 조회 후 launch-hook CONTINUE 전송
  - LifecycleHookInitializer.java (신규): Spring Boot 시작 시 completeLaunch() 호출
  - LifecycleHookConsumer.java (수정): LAUNCHING 이벤트 수신 시 Queue1 활성화
  - GracefulShutdownConfig.java (수정): 종료 시 Queue1 비활성화 + 5초 대기

버그 수정 사항:

1. LifecycleHookService.java — IMDSv1 → IMDSv2 수정
   - 팀원 코드: 단순 GET으로 메타데이터 조회 (IMDSv1 방식)
   - Launch Template에 IMDSv2 전용 설정 → IMDSv1 요청 거부됨
   - 수정: PUT 요청으로 토큰 발급 → GET 요청 시 X-aws-ec2-metadata-token 헤더 포함

2. build.gradle — AWS SDK 버전 충돌 해결
   - 팀원 코드: autoscaling:2.20.0 명시 → Spring Cloud AWS BOM(2.21.46)과 충돌
   - 증상: NoClassDefFoundError: QueryParametersToBodyInterceptor
   - 해결: 명시적 버전 제거 (BOM 관리 방식으로 전환) + aws-query-protocol 의존성 추가

3. LifecycleHookConsumer.java — TERMINATING 처리 제거
   - 원래 TERMINATING 이벤트도 SQS로 처리 시도했으나 deadlock 발생
   - 이유: GracefulShutdown(SIGTERM 수신 시 동작)은 CONTINUE 이후에 SIGTERM이 와야 하는데,
     CONTINUE를 보내는 주체가 SIGTERM 이후에 동작하는 구조 → 순환 교착
   - 해결: TERMINATING 처리는 Lambda로 분리
