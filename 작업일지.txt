프로젝트 개요
--------------------------------------------------------------------------------

[시스템 아키텍처]

  사용자 → CloudFront → WAF → ALB → EC2 (ASG, project-asg)
                                          ↕
                              RDS (MySQL, ap-southeast-2)
                              ElastiCache (Redis, TLS)
                              SQS (대기열 처리, Lifecycle Hook)
                              SES (이메일 인증)

[팀 역할 분담]
- 주영 + 상우: 예약 시스템 메인 비즈니스 로직 (대기열, 예약, Auto Scaling 설계)
- 세창: 보안 코드 구현 + AWS 인프라 배포 전담

[핵심 설계 목표]
1. Scale Out/In 시 진행 중인 요청이 유실되지 않도록 Graceful Shutdown 구현
2. 대기열 진입부터 예약 확정까지 HMAC 토큰으로 요청 위변조 방지
3. 이메일 인증으로 중복 계정 및 비정상 사용자 차단
4. CloudFront + WAF로 DDoS/봇 트래픽 1차 차단

■ 문제 1: S3 jar 다운로드 404 오류

증상: EC2 시작 시 "An error occurred (404) when calling the HeadObject operation"

원인 파악 과정:
1. IAM 권한 문제 의심 → Role 정책 재확인 → 정상
2. S3 리전 플래그 누락 의심 → --region ap-northeast-2 추가 → 동일 오류
3. S3 콘솔에서 실제 버킷명 직접 확인
   → 실제 버킷명: project-reservation-jar-247448832103-ap-northeast-2-an
   → User Data에 입력한 버킷명: project-reservation-jar (짧은 이름)
   → 원인: AWS가 버킷 생성 시 계정 ID + 리전을 자동으로 추가한 긴 이름으로 생성

해결: Launch Template User Data의 S3 URI를 실제 버킷명으로 수정

교훈: S3 버킷 생성 시 콘솔에서 표시되는 실제 이름과 의도한 이름이 다를 수 있음
      → 배포 전 S3 콘솔에서 실제 버킷명 반드시 확인

■ 문제 2: ALB Target Group 지속 unhealthy

증상: S3 다운로드 성공, 앱 실행 중이지만 ALB Target Group이 계속 unhealthy
      → ASG가 비정상 인스턴스로 판단하고 교체 루프 발생

원인 파악 (3단계):

단계 1 — 헬스체크 경로 문제
- 기존 경로 "/" → Spring Security anyRequest().authenticated() → 401 반환 가능
- /actuator/health로 변경 → 여전히 unhealthy

단계 2 — Actuator 미포함
- build.gradle에 spring-boot-starter-actuator 자체가 없었음
- /actuator/health 경로 존재하지 않아 404 반환 → unhealthy
- actuator 추가 후 재빌드/재배포 → 여전히 unhealthy

단계 3 — HTTPS 강제 설정 충돌 (근본 원인)
- Fleet Manager로 EC2 접속하여 app.log 직접 확인 → 앱은 정상 기동 중
- 분석:
  ALB는 EC2에 HTTP(8080)로 헬스체크 전송
  SecurityConfig의 requiresChannel().anyRequest().requiresSecure() 설정이
  모든 HTTP 요청을 HTTPS로 302 리다이렉트
  → ALB가 302를 받으면 unhealthy 판정
- 근본 원인: HTTPS 강제는 CloudFront/ALB 레벨에서 이미 처리 중
  → EC2 내부에서 이중으로 강제할 필요 없음

해결: SecurityConfig에서 requiresChannel 블록 제거

■ 문제 3: RDS 연결 실패 — 크로스 리전

증상: "Communications link failure", "SocketTimeoutException: Connect timed out"
      Hibernate SessionFactory 초기화 중 DB 연결 타임아웃

원인 파악:
- EC2 접속 방법 탐색:
  * SSH: 프라이빗 서브넷 → 퍼블릭 IP 없음 → 불가
  * SSM Session Manager: "no valid credentials" (VPC 엔드포인트 없음)
  * Fleet Manager → 성공적으로 터미널 접속
- app.log에서 RDS 엔드포인트 확인:
  reservation.c9iqgkqq2vql.ap-southeast-2.rds.amazonaws.com
  → ap-southeast-2 = 시드니! EC2는 서울(ap-northeast-2)
- 원인: 팀원이 RDS 생성 시 실수로 시드니 리전 선택
- 크로스 리전이라 EC2 보안 그룹 참조 불가 → 0.0.0.0/0 임시 개방

해결 (임시): 시드니 RDS 보안 그룹 3306 포트 0.0.0.0/0 인바운드 추가
보안 주의: 추후 서울 리전으로 RDS 이전 또는 특정 IP만 허용하도록 변경 필요

■ 문제 4: Redis(ElastiCache) 연결 실패 — TLS 미설정

증상:
- "Unable to connect to master.project-reservation-redis.nm3ono.apn2.cache.amazonaws.com/<unresolved>:6379"
- "RedisCommandTimeoutException: Connection initialization timed out after 3 second(s)"

원인 파악 (6단계):
1. 보안 그룹 확인 → EC2/ElastiCache 모두 6379 인바운드 규칙 존재 → 정상
2. DNS 해석 확인 → nslookup으로 IP 정상 조회됨 → DNS 문제 아님
3. TCP 연결 테스트:
   timeout 5 bash -c 'cat < /dev/tcp/10.0.129.216/6379' → 연결 실패
   같은 VPC임에도 TCP 연결 자체가 차단됨
4. ElastiCache 보안 그룹 소스를 CIDR → EC2 보안 그룹 ID로 변경 → 여전히 실패
5. ElastiCache 설정 확인:
   "In-transit encryption: 활성화됨, 전송 암호화 모드: 필수(required)"
   → TLS 연결만 허용하는데 앱은 일반 TCP로 시도 → ElastiCache가 즉시 연결 거부
6. TLS 연결 테스트로 가설 검증:
   openssl s_client -connect master...apn2.cache.amazonaws.com:6379
   → CONNECTED, TLSv1.2 성공 → 네트워크/보안 그룹은 정상, 앱의 TLS 설정 누락이 원인

해결: application.yml에 spring.data.redis.ssl.enabled: true 추가

교훈: ElastiCache 생성 시 In-transit encryption 기본 활성화 여부를 반드시 확인할 것
      TCP 연결 테스트가 실패해도 TLS 연결 테스트를 별도로 시도해야 정확한 진단 가능

- 원인: Spring Cloud AWS 3.x에서 SES 자동 구성이 해당 구체 타입의 빈을 등록하지 않음
        MailSender 인터페이스로 등록함

트러블슈팅 2: SES API 호출 시 403 Forbidden
- 원인 분석:
  * Spring Security CSRF 보호 활성화 상태에서 POST 요청에 CSRF 토큰 필요
  * GET으로 토큰 획득 후 X-XSRF-TOKEN 헤더에 포함 재요청 → 여전히 403
  * Spring Security 6에서 CSRF 방식 변경:
    기존: 쿠키 값 = 헤더 값이면 통과
    변경: XOR 마스킹 적용 → 쿠키 원본값을 헤더에 그대로 보내면 검증 실패
- 근본 해결:
  REST API는 stateless이므로 CSRF 보호 불필요
  (CSRF는 브라우저 세션 기반 공격 방어 → 이 API는 HMAC 토큰으로 인증)
  SecurityConfig .csrf(csrf -> csrf.disable()) 으로 변경

결과: 이메일 발송 성공, 인증 코드 수신 확인

[2026-06-07] 세션 4 — ASG Lifecycle Hook 통합 및 동작 검증
--------------------------------------------------------------------------------

■ Lifecycle Hook 개요 및 필요성

ASG Scale Out/In 시 단순히 인스턴스를 시작/종료하면 다음 문제가 발생:
- Scale Out: 앱이 완전히 기동되기 전에 ALB가 트래픽을 보내 오류 발생
- Scale In: 진행 중인 HTTP 요청이 SIGTERM으로 강제 종료되어 클라이언트에 오류 반환

Lifecycle Hook은 인스턴스를 Pending:Wait / Terminating:Wait 상태로 잡아두어
필요한 작업(앱 기동 완료 확인, 진행 중 요청 처리 완료)을 마친 후 CONTINUE 신호를 보내
정상적인 흐름으로 진행하도록 제어하는 메커니즘.

■ 설계한 Lifecycle Hook 흐름

[Scale Out — launch-hook]
  ASG Scale Out 결정
  → EC2 인스턴스 시작 (Pending:Wait)
  → launch-hook 이벤트 → lifecycle-hook-queue (SQS)
  → Spring Boot 앱이 SQS 메시지 수신 (LifecycleHookConsumer)
      * auto-enabled ON이면 Queue1(대기열) 활성화
      * Warm Pool 페이즈이면 활성화 건너뜀
  → 앱 완전 기동 후 LifecycleHookInitializer가 CONTINUE 신호 전송
  → 인스턴스 InService 상태 진입, ALB에 트래픽 수신 시작

[Scale In — terminate-hook]
  ASG Scale In 결정
  → EC2 인스턴스 종료 대기 (Terminating:Wait)
  → terminate-hook 이벤트 → lifecycle-hook-terminate-queue (SQS)
  → Lambda(lifecycle-hook-terminate) SQS 수신
  → GracefulShutdownConfig: Queue1 비활성화 (신규 요청 차단) + 5초 대기 (진행 중 요청 완료)
  → Lambda가 CONTINUE 신호 전송
  → SIGTERM 수신 → 앱 종료

핵심: CONTINUE를 보낸 후 SIGTERM이 오는 것이므로,
      앱이 종료되기 전에 반드시 요청 처리를 완료하고 나서 CONTINUE를 보내는 순서 보장

■ 코드 통합 — 팀원(상우) 코드 버그 수정

팀원이 추가한 코드:
- LifecycleHookService.java: 인스턴스 ID 조회 + launch-hook CONTINUE 전송
- LifecycleHookInitializer.java: 앱 시작 시 completeLaunch() 호출
- LifecycleHookConsumer.java: SQS 메시지 수신 처리

버그 1: IMDSv1 방식으로 인스턴스 ID 조회 → Launch Template이 IMDSv2 전용이라 거부됨

  팀원 코드 (IMDSv1):
    URL url = new URL("http://169.254.169.254/latest/meta-data/instance-id");
    return new BufferedReader(new InputStreamReader(url.openStream())).readLine();

  수정 코드 (IMDSv2):
    1단계: PUT 요청으로 세션 토큰 발급
      URL tokenUrl = new URL("http://169.254.169.254/latest/api/token");
      conn.setRequestMethod("PUT");
      conn.setRequestProperty("X-aws-ec2-metadata-token-ttl-seconds", "21600");
      String token = reader.readLine();
    2단계: GET 요청 시 토큰 헤더 포함
      conn.setRequestProperty("X-aws-ec2-metadata-token", token);

  배경: IMDSv2는 SSRF 공격으로 메타데이터를 탈취하는 공격 벡터를 차단하기 위해 도입됨
        토큰 기반 방식이므로 단순 GET 요청으로는 메타데이터에 접근 불가

버그 2: AWS SDK 버전 충돌 → NoClassDefFoundError: QueryParametersToBodyInterceptor

  팀원 코드 (충돌):
    implementation 'software.amazon.awssdk:autoscaling:2.20.0'

  문제 원인:
    Spring Cloud AWS BOM이 awssdk 2.21.46 버전을 관리하는데,
    명시적으로 다른 버전(2.20.0)을 지정하면 내부 의존성 간 버전 불일치 발생
    autoscaling SDK가 쿼리 파라미터를 HTTP Body로 변환하는 QueryParametersToBodyInterceptor 클래스를
    해당 버전에서 찾지 못함

  수정:
    implementation 'software.amazon.awssdk:autoscaling'           # 버전 BOM에 위임
    implementation 'software.amazon.awssdk:aws-query-protocol'    # 누락된 프로토콜 의존성 추가

버그 3: TERMINATING 이벤트를 SQS Consumer에서 처리 시 순환 교착(deadlock)

  문제 구조:
    SIGTERM 수신 시 GracefulShutdown 동작
    → 하지만 SIGTERM은 ASG가 CONTINUE를 받은 후에 보냄
    → CONTINUE를 SQS Consumer에서 처리하려면 앱이 살아있어야 함
    → 앱이 종료되는 중에 SQS 메시지를 처리해야 하는 구조 → 순환 불가

  해결: TERMINATING CONTINUE 처리를 Lambda 함수로 분리
    - Lambda는 앱과 독립적으로 동작
    - EC2가 Terminating:Wait 진입 → SQS 메시지 발행 → Lambda 수신
    - Lambda가 CONTINUE 전송 → SIGTERM 발송 → GracefulShutdown 실행

■ AWS 설정

1. SQS 대기열 2개
   - lifecycle-hook-queue: launch-hook 이벤트 수신 (Spring Boot Consumer)
   - lifecycle-hook-terminate-queue: terminate-hook 이벤트 수신 (Lambda Consumer)

2. IAM Role: project-asg-lifecycle-role
   - ASG가 SQS에 메시지를 발행할 수 있도록 허용

3. Lifecycle Hook 설정
   [launch-hook]
   - 트랜지션: autoscaling:EC2_INSTANCE_LAUNCHING
   - 알림 대상: lifecycle-hook-queue
   - 하트비트 타임아웃: 120초 (앱 기동 ~22초 + 여유 시간 고려)
   - 기본 동작: CONTINUE

   [terminate-hook]
   - 트랜지션: autoscaling:EC2_INSTANCE_TERMINATING
   - 알림 대상: lifecycle-hook-terminate-queue
   - 하트비트 타임아웃: 60초
   - 참고: 콘솔 UI에서 SQS를 알림 대상으로 설정하는 기능 미지원
     → CloudShell CLI로 설정:
     aws autoscaling put-lifecycle-hook \
       --lifecycle-hook-name terminate-hook \
       --auto-scaling-group-name project-asg \
       --lifecycle-transition autoscaling:EC2_INSTANCE_TERMINATING \
       --notification-target-arn arn:aws:sqs:...:lifecycle-hook-terminate-queue \
       --role-arn arn:aws:iam::...:role/project-asg-lifecycle-role

4. Lambda 함수: lifecycle-hook-terminate
   - 런타임: Python 3.12
   - 트리거: lifecycle-hook-terminate-queue (SQS)
   - IAM: AmazonSQSFullAccess, AmazonEC2FullAccess

   최종 코드:
   ```python
   import json
   import boto3
   from botocore.exceptions import ClientError

   def lambda_handler(event, context):
       autoscaling = boto3.client('autoscaling', region_name='ap-northeast-2')
       for record in event['Records']:
           body = json.loads(record['body'])
           if body.get('LifecycleTransition') == 'autoscaling:EC2_INSTANCE_TERMINATING':
               instance_id = body['EC2InstanceId']
               try:
                   autoscaling.complete_lifecycle_action(
                       LifecycleHookName=body['LifecycleHookName'],
                       AutoScalingGroupName=body['AutoScalingGroupName'],
                       LifecycleActionToken=body['LifecycleActionToken'],
                       LifecycleActionResult='CONTINUE',
                       InstanceId=instance_id
                   )
                   print(f"Terminate hook CONTINUE 전송 완료 - instanceId: {instance_id}")
               except ClientError as e:
                   if e.response['Error']['Code'] == 'ValidationError':
                       # 만료된 토큰(스테일 메시지) → 정상 처리 후 SQS에서 삭제
                       print(f"[SKIP] 이미 완료된 액션 - instanceId: {instance_id}")
                   else:
                       raise
       return {'statusCode': 200}
   ```

■ 트러블슈팅

문제 1: launch-hook "No active Lifecycle Action found"
- 상황: LifecycleHookInitializer가 CONTINUE 전송 시도 → 오류
- 원인 분석:
  * launch-hook 발생 시각: 01:29:02
  * 앱 CONTINUE 시도: 01:30:18 → 76초 경과
  * 하트비트 타임아웃: 60초 → 이미 만료, 기본 동작(CONTINUE)으로 자동 처리됨
  * 결과: 인스턴스는 정상 시작됐으나 명시적 CONTINUE는 실패
- 해결: launch-hook 하트비트 타임아웃을 60초 → 120초로 증가
  aws autoscaling put-lifecycle-hook --heartbeat-timeout 120 ...
- 결과 확인: "Launch hook 완료 신호 전송 - instanceId: i-086153ad0bfd56eae" ✓

문제 2: Lambda가 스테일 SQS 메시지를 반복 재시도
- 상황: 이전 테스트에서 생성된 만료 토큰 메시지가 계속 Lambda를 호출하며 에러 발생
- 원인:
  SQS는 Lambda가 예외를 throw하면 메시지를 삭제하지 않고 재전송
  ValidationError("No active Lifecycle Action")를 catch하지 않아 계속 retry
- 해결: ClientError 예외 처리 추가
  * ValidationError → 로그 출력 후 정상 반환 (SQS가 메시지 삭제)
  * 그 외 예외 → raise (재시도 유지)

문제 3: terminate-hook 설정 시 콘솔에서 SQS 알림 대상 미지원
- 상황: AWS 콘솔 UI에서 Lifecycle Hook 생성 시 알림 대상으로 SQS 선택 불가
- 해결: CloudShell에서 CLI 명령어로 직접 설정

문제 4: 후크 이름에 언더스코어(_) 사용 시 코드와 불일치
- 상황: 콘솔에서 launch_hook, terminate_hook으로 생성 → 코드에서 launch-hook, terminate-hook 참조
- 해결: 후크 삭제 후 하이픈(-) 사용으로 재생성
