[2026-06-05] 세션 2 — EC2 배포 디버깅 및 앱 실행

[S3 URI 오류 수정]
- 이전 세션에서 User Data의 S3 버킷명이 잘못 설정되어 있었음
  - 잘못된 버킷명: project-reservation-jar
  - 실제 버킷명: project-reservation-jar-247448832103-ap-northeast-2-an
- Launch Template 버전 5 생성: S3 URI 수정
- ASG 0 → 1로 올려 새 인스턴스 기동 → 시스템 로그에서 S3 다운로드 성공 확인

[ALB 헬스체크 — unhealthy 디버깅]
- 원인 1: spring-boot-starter-actuator 미포함
  - /actuator/health 엔드포인트 자체가 없었음
  - build.gradle에 spring-boot-starter-actuator 추가
- 원인 2: SecurityConfig의 requiresChannel().anyRequest().requiresSecure()
  - ALB가 HTTP로 헬스체크 → Spring Security가 302 리다이렉트 → unhealthy
  - HTTPS는 CloudFront/ALB에서 이미 처리하므로 requiresChannel 제거
- 재빌드(gradlew.bat bootJar) → S3 재업로드 → ASG 재시작

[RDS 연결 실패]
- app.log 확인 (Fleet Manager → Session Manager로 EC2 접속)
  - 오류: Communications link failure / SocketTimeoutException
  - EC2(서울, ap-northeast-2)에서 RDS(시드니, ap-southeast-2) 3306 포트 연결 불가
- 원인: RDS가 실수로 시드니 리전에 생성되어 있었고 보안 그룹에 3306 규칙 없었음
- 임시 조치: 시드니 RDS 보안 그룹에 MySQL/Aurora 3306 포트 0.0.0.0/0 인바운드 규칙 추가
  - [주의] 추후 상우와 상의하여 RDS 서울 이전 또는 IP 제한으로 교체 필요

[Redis TLS 연결 실패 해결]
- app.log 분석: Redis 연결 타임아웃 (io.lettuce.core.RedisCommandTimeoutException)
- 원인: ElastiCache에 전송 중 암호화(TLS) 필수 설정되어 있었으나 앱은 일반 연결 시도
- openssl s_client 테스트로 TLS 연결 정상 확인 (CONNECTED, Verification: OK, TLSv1.2)
- application.yml에 spring.data.redis.ssl.enabled: true 추가
- 재빌드 → S3 재업로드 → ASG 재시작

[배포 최종 성공]
- Started ReservationApplication in 25.322 seconds
- HikariPool-1 (RDS) 연결 성공
- SQS Listener 컨테이너 2개 정상 시작
- ALB Target Group → healthy 확인
- 문제 해결 요약:
  1. S3 버킷명 오류 수정 (Launch Template v5)
  2. spring-boot-starter-actuator 추가 (/actuator/health 엔드포인트)
  3. SecurityConfig requiresChannel 제거 (ALB HTTP 헬스체크 302 리다이렉트 문제)
  4. 시드니 RDS 보안 그룹 3306 포트 0.0.0.0/0 개방
  5. Redis SSL 설정 추가 (spring.data.redis.ssl.enabled: true)
